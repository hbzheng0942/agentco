# T-20260707-008 result (executor-code/executor-code-hi)

结论：`_llm()` 以 `ds-chat` 调本地 LiteLLM 端点 `http://127.0.0.1:4000/v1/chat/completions`，客户端超时固定 `12` 秒；对当前“快路径规则直通 → concierge → bridge 兜底 → 规则/ inbox 再兜底、消息永不丢”的入站架构，这个值**基本合理，但明显偏向快失败，不偏向最大化 bridge 命中率**。

## 交付物

### 1) 事实定位
- 超时定义在 `bin/bridge.py:46`：`def _llm(text, timeout=12):`
- 调用模型在 `bin/bridge.py:47`：`"model": "ds-chat"`
- 调用端点在 `bin/bridge.py:50`：`http://127.0.0.1:4000/v1/chat/completions`
- 实际生效的网络超时在 `bin/bridge.py:54`：`urllib.request.urlopen(r, timeout=timeout)`

### 2) 端点背后的实际模型链
- `ds-chat` 在 `config/litellm.yaml:3-9` 映射到 `deepseek/deepseek-v4-flash`
- 且显式关闭 `thinking`，这是在压低单轮延迟：`config/litellm.yaml:7-9`
- LiteLLM 路由层全局配置是 `num_retries: 2`、`timeout: 120`：`config/litellm.yaml:45-54`
- `ds-chat` 还配置了 fallback 到 `kimi-long`：`config/litellm.yaml:47-49`

### 3) 为什么说 12 秒“基本合理”
依据不是“模型一定很快”，而是**代码把 bridge 定位成兜底分诊器，不是主交互通道**：

- 设计文档明确写了 bridge 是**网关层一次 ds-chat 调用**，并且“任何一层失败降级，消息永不丢”：`kb/00-core/constitution.md:36-41`
- 当前入站主路径已变成：
  - 规则快路径直通：`bin/feishu_gateway.py:208-219`
  - 其余消息先进 concierge：`bin/feishu_gateway.py:221-233`
  - concierge 失败才降 bridge：`bin/feishu_gateway.py:230-232`
  - bridge 再失败就规则解析/ inbox：`bin/feishu_gateway.py:269-278`
- 慢车道是后台线程，不阻塞单线程 HTTP 服务：`bin/feishu_gateway.py:221`

所以，`12s` 的作用更像是：
- 给 bridge 一次“够用但不恋战”的窗口；
- 超时就快速让位给规则解析或 inbox；
- 保障手机端不要长时间无反馈。

在这个定位下，`12s` 是**可自洽**的。

### 4) 为什么又说它“偏快失败”
`12s` 明显短于 LiteLLM 自身的容错预算：

- client 侧只等 `12s`：`bin/bridge.py:46-55`
- proxy/router 侧却允许 `120s` 且 `2` 次重试：`config/litellm.yaml:45-54`

这意味着：
- 一旦 `ds-chat` 出现尾延迟，bridge 很可能**先于** LiteLLM 的重试/fallback 完成就直接放弃；
- `ds-chat -> kimi-long` 这条兜底链，在 bridge 这里未必来得及真正发挥；
- 结果不是“消息丢失”，而是更频繁地落到：
  - `parse_dispatch()` 规则解析：`bin/feishu_gateway.py:269-273`
  - 或 inbox：`bin/feishu_gateway.py:275-278`

所以，`12s` 保护的是**响应性**，牺牲的是**自由文本分诊成功率**。

### 5) 结合“考虑 ds-chat 延迟”的最终判断
**最终判断：合理，但偏保守。**

- 如果目标是：  
  **“入站不能久等，宁可降级，也别在 bridge 上卡住”**  
  那 `12s` 合理。
- 如果目标是：  
  **“尽量让自由文本都被 bridge 正确结构化，不想太早掉 inbox/规则兜底”**  
  那 `12s` 偏紧。

结合现有架构，我更倾向前者，因为：
1. bridge 已不是主入口，而是 concierge 失败后的兜底；
2. bridge 失败不会丢消息；
3. `ds-chat` 用的是 flash 档且禁思考，本就朝低延迟配置；
4. 入站网关更怕“长时间没回音”，不太怕“降级到 inbox”。

因此我的结论是：  
**对“入站分诊”这个场景，12 秒是合理的快失败阈值；但它并不追求吃满 LiteLLM 的重试/fallback 能力，ds-chat 抖动时会增加误降级概率。**
